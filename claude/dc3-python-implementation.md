**Purpose.** This document records the *execution* of the port: what was built in each phase,
what was verified, and — most importantly — **where the implementation departed from the plan and
why**. The plan says what should happen; this says what did.

### The survey — [`dc3-original-implementation.md`](dc3-original-implementation.md)

A full survey of the C++ code base at `/Users/westfallold/Work/scripts/dc3` and its dependency
closure, cross-checked against a real production campaign. It is the authority on *what the
existing code does*, and the port is written against it rather than against the C++ directly.

What it establishes that matters most for implementation:

- **The algorithm does not live in `dc3/`.** It migrated into `libraries/vdf.cpp`,
  `correlation.cpp`, `cnvlv.cpp`, `spectrum.cpp` and `contfit.cpp` between 2006 and 2013. The
  `dc3/` directory is drivers and a dead interactive UI (§4, §9).
- **`DC3_express` is the only working end-to-end driver.** Eight of nineteen executables no
  longer compile, and the prebuilt binaries do not run (§1, §5). **There is no live oracle.**
- The full control flow of `DC3_express` (§6) and of the `VDF`/`Correlation`/`cnvlv` core (§8),
  quoted at the source level — this is the specification the port reproduces.
- **Nine defects**, including three argument-indexing bugs and the `win.invs`/`win.inve` mix-up
  at `vdf.cpp:487` that the port must not inherit (§14).
- **The archived outputs were not produced by the code now on disk** (§16.0). Source
  modification times span 2013–2016 against a February 2013 campaign, so archived `.db` and
  FITS products are *indicative*, never authoritative.
- **The W11 §5 demonstration data exists**, at
  `/Volumes/seshat/SPSPK_rdx/kinematics/mg/U06918/vdf_dec08/` (§16.8) — the only fixture set
  tied to published numbers.

## Ground rules carried into implementation

Collected here because they are easy to violate accidentally and expensive to unpick later. Each
is stated in full in the plan; this is the checklist.

| Rule | Where |
|---|---|
| The galaxy's flux distribution is **never** redistributed. De-redshifting is an integer pixel shift. | Phase 2 |
| Resolution matching is **preparation only** — never inside the cost function. | Phase 2 |
| **No deconvolution**, anywhere. | Phase 2 |
| Template preparation runs **once per execution**, never per spectrum. | Phase 2 |
| `sres` vectors are **pre-pixelized** on input. The code cannot check this; document it everywhere a user will look. | Phase 2 |
| Templates are treated as **noise-free**; only the galaxy carries errors. | Phase 2, science question 4 |
| **Never vendor, copy or adapt `ppxf` source.** Import it. A clean-room reimplementation must be written from the papers. | External dependencies, Phase 3 |
| Config keys map **1:1** to in-code parameters. No renaming, no derived keys. | Phase 1 |
| `FuncPar` wraps **third-party** functions only, and points at their documentation rather than reproducing it. Internal parameters get a hand-written `ParSet`. | Phase 1 |
| Documentation is generated by reflection so it cannot drift. | Phase 1, Phase 8 |
| No package code reads `/Volumes/seshat` at run time. | Test data |
| Backwards compatibility with the C++ formats and CLI is **not** a goal. | Context |

## Phase 1 — Package infrastructure

🔵 **In progress.**

### `dc3/pkg/` — ✅ complete (commit `94aeb32`)

Adapted from PypeIt, and verified working from an editable install: the package imports, both
data paths resolve, the logger emits, and the cache builds correct remote URLs.

| Module | Notes |
|---|---|
| `exceptions.py` | `DC3Error` and five subclasses. Added `DC3ParameterError` and `DC3ResolutionError` beyond PypeIt's set — the latter for the two resolution cases that must never pass silently: a kernel requiring deconvolution, and a kernel below the `varsmooth` floor |
| `logger.py` | Drops PypeIt's `STEP` level (a Dashboard feature with no counterpart) and its numpy `RankWarning` filter |
| `cache.py` | GitHub-only. Drops the `s3_cloud` host, the PyGithub repository-*listing* helpers, and `git_most_recent_tag` — so no `github` or `requests` dependency |
| `dc3data.py` | Two registered paths: `tests` and `templates`, both GitHub-hosted |

**Branch resolution is retained in full, and it is load-bearing.** `_build_remote_url` puts the
checked-out branch into the download URL, so a fixture added on a feature branch is fetched from
*that* branch. Verified empirically that `pygit2.Repository` performs **upward discovery** — from
`pypeit/pkg` it resolved `/Users/westfall/Work/packages/pypeit/.git` and reported the branch — which
is why this works under `tox`, where the package is installed beneath `.tox/`, still inside the
checkout. Without it the URL silently falls back to `main` and CI fails on any branch that adds
data, with an error that looks nothing like its cause. **`pygit2` is therefore in the `test`
extra**, not optional for testing.

### `dc3/par/` — ⬜ not started

This is where the first structural decision has to be settled. Two decisions are deliberately
left open for the implementation to settle, both by prototyping rather than by argument:

1. **Whether `ParSet` is built on `pydantic` v2** or on PypeIt's hand-rolled design. Prototype one
   parameter set both ways first. What pydantic does not give free: `to_rst_table`,
   `to_header`/`from_header`, and the layered default→file→CLI merge.
2. **Whether the datamodel splits I/O from validation** or stays a single `DataContainer`-style
   class. `dc3/results.py` (Phase 4) is the test case.

Read the **`funcpar_rebase`** branch of `~/Work/packages/pypeit` before writing anything — it is
the single source for both `ParSet` and `FuncPar`, and supersedes `funcpar_update`.

Carry the rule the plan states with it: **`FuncPar` wraps third-party functions only**, deferring
to their documentation rather than reproducing it; anything internal to `dc3` gets a hand-written
`ParSet` subclass with full `dtype`, `options` and `descr`.
