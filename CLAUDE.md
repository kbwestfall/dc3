# DC3 — working notes for Claude

`dc3` is a Python port of a C++ code implementing the detector-censored
cross-correlation method of Westfall, Bershady & Verheijen (2011, ApJS 193, 21).

## Read these first

The design record lives in `claude/` and is authoritative:

| Document | What it is |
|---|---|
| `dc3-original-implementation.md` | Survey of the original C++ code base. The authority on what the existing code does. |
| `dc3-python-port-plan.md` | The phased plan. The document implementation is measured against, and the one to amend when reality disagrees with it. |
| `dc3-python-implementation.md` | The running record: what was built in each phase, and **every deviation from the plan**. |
| `plan-reassessment.md`, `notes` | Support material. Consult when a plan decision looks arbitrary; not maintained as reference. |

**Append a change-log entry to any of these documents whenever you edit it**,
most-recent-at-bottom.

## Hard rules

These are easy to violate accidentally and expensive to unpick.

1. **Never vendor, copy, or adapt `ppxf` source.** Its license prohibits
   redistribution; a copied helper would void this package's BSD-3 license.
   Import it. Clean-room reimplementation from the published papers is fine; a
   line-by-line translation is not, in any language. See `licenses/README.rst`.
2. **No package code may read `/Volumes/seshat` at run time.** It is an external
   RAID. It appears only as an argument to the one-time staging script.
3. **Test data goes in `dc3/data/tests/`, never `dc3/tests/data/`.** `dc3/tests/`
   holds test *code* only.
4. **The galaxy spectrum's flux distribution is never redistributed.**
   De-redshifting is an integer pixel shift. No interpolating alternative.
5. **Resolution matching is template preparation only** — once per run, never
   inside the cost function, and never on the galaxy.
6. **No deconvolution, anywhere.**
7. **Templates are noise-free.** Only the galaxy carries errors.
8. **Config keys map 1:1 to in-code parameters.** No renaming between file and
   object, no derived keys that exist in only one of the two.
9. **`FuncPar` wraps third-party functions only**, deferring to their
   documentation rather than reproducing it. Anything internal to `dc3` gets a
   hand-written `ParSet` with full `dtype`, `options` and `descr`.
10. **Backwards compatibility with the C++ formats and CLI is not a goal.**

## Conventions

- **Always use explicit condition checks.** Never rely on the truthiness or
  falsiness of a non-boolean object: write `if x is None`, `if len(x) == 0`,
  `if x != 0`, not `if not x` or `if x`. Truthiness on an actual `bool` is fine.
- **Every `assert` in a test carries a message describing the expected
  behaviour.** A bare assertion reports only that a comparison failed; the
  message is what tells the next reader what was supposed to happen.
- **Anything that wraps onto multiple lines** — a signature, a call, an `if`
  condition, a collection literal — puts its contents on the line *below* the
  opening construct, indented, with the closing bracket (and any trailing colon)
  alone on a line aligned with the line that opened it:

  ```python
  def config_lines(
      self, section_name=None, exclude_defaults=False, fallback_comment=None
  ):

  lines += value.config_lines(
      section_name=f'{_section}.{key}', exclude_defaults=exclude_defaults
  )

  if (
      self.fit.moments > 2 and self.template.sigma_floor > 0.0
  ):
  ```
- **Lines are at most 99 characters.** Enforced by `tox -e codestyle`, which
  configures `pycodestyle` from `tox.ini` to check `E9` (syntax/runtime errors)
  and `E501` (line length) and nothing else.
- **No nested function definitions.** A helper belongs at module level, private
  by a leading underscore if it is not part of the interface. The exception is
  test code, where a closure over the fixture under test is often the clearest
  way to express a check.
- **Imports go at the top of the file.** The one exception is a script: the
  imports a `ScriptBase` subclass needs belong inside its `main`, because every
  registered entry point is imported when the console scripts are resolved, so
  a module-level import of the heavy machinery makes `--help` pay for it.
- **Avoid `import ... as`.** Industry-standard aliases (`import numpy as np`)
  are fine; otherwise import the module or name directly.
- **Any docstring containing a backslash is an r-string** (`r"""`), so that
  LaTeX in `:math:` roles reads as written rather than being double-escaped.
- Docstrings are **NumPy style**, rendered by `numpydoc`. References to objects
  in other packages take an **explicit role** so that intersphinx resolves them
  — `` :class:`numpy.ndarray` ``, `` :func:`astropy.stats.sigma_clip` `` — not
  the default role. Bare package names in prose are literals: ``` ``ppxf`` ```.
- Parameter, datamodel and bitmask documentation is **generated by reflection**
  so it cannot drift from the code. Keep that property.
- **Three places record a change, and they do not overlap:**

  | Where | What goes there |
  |---|---|
  | Commit message | Very short — a single subject line. **No attribution or co-author trailers.** |
  | `doc/releases/` | Brief, simple statements of the work completed. No rationale. There is no root `CHANGES.rst`. |
  | `claude/dc3-python-implementation.md` | The decisions taken, the reasoning behind them, and every deviation from the plan. |
- Configuration files are **TOML**, read with the standard-library `tomllib`.
- Adapted code carries an attribution note in its module docstring naming the
  source project and file.

## Environment

**Development is on macOS.** Shell commands must work with the BSD userland, not
the GNU one. The differences that actually bite:

| Tool | Watch for |
|---|---|
| `sed` | No `\b` word boundary, and `-i` requires an explicit backup suffix (`sed -i ''`). For anything beyond a literal substitution, use Python instead. |
| `grep` | Use `-E` for extended regular expressions; `\b` is unreliable. |
| `date`, `stat`, `readlink` | Different flags from the GNU versions. |

Python itself is installed via Homebrew.

Development install (Python ≥ 3.12), into the virtual environment `$ENVS_HOME/dc3`:

```
python3 -m venv $ENVS_HOME/dc3
source $ENVS_HOME/dc3/bin/activate
pip install -e ".[dev]"
```

Virtual environments live in `$ENVS_HOME` (`~/.virtualenvs`), never in the
repository — an in-tree environment named `dc3` would collide with the `dc3/`
package directory. Python itself is installed via Homebrew.

Run the tests with `pytest dc3` or, across the matrix, with `tox`.
